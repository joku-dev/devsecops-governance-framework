## Release Identity

| Field | Value |
|---|---|

| Release line | Repository adoption and operations |
| Classification | Minor backward-compatible capability release since `v0.2.0-public-adoption` |
| Intended use | Public evaluation and controlled report-only operation |
| Governance change | `GCR-2026-103` |
| Evidence observation | Accepted ha-CPsWMS mainline and staging evidence from 19 September 2026 |

Publication is authoritative only when the directly signed tag points to
reviewed `main` and the [GitHub Release](https://github.com/joku-dev/devsecops-governance-framework/releases/tag/v0.3.0-public-adoption)
is published. The tag fixes the complete repository revision. Dated consumer
evidence retains its own producer time and does not become fresh merely because
this release is published.

## Changes Since v0.2.0

### Evidence and measured controls

- Typed vulnerability and CycloneDX SBOM intake now verifies producer context,
  artifact hashes, subject binding, integrity and Freshness.
- Evidence Trust and control-level assurance cover all applicable L1 evidence
  types conservatively; missing proof remains `unverified`.
- ha-CPsWMS has real tool evidence from tests, Bandit, Ruff, Trivy, five container
  images and five CycloneDX SBOMs.
- A separate staging deployment records approval, immutable image identity,
  runtime security boundaries, health, function, persistence, outage, recovery
  and restart checks.

### Viewer and operations

- The Governance Workspace is the primary viewer application and integrates the
  technical results, Evidence Trust, replay deviations, measured L1 coverage,
  staging evidence, portfolio state and repository Self-Security.
- Typed evidence, staging evidence and portfolio updates use scoped intake and
  publication paths with append-only history and protected-main PRs.
- The capacity assessment and deterministic simulation describe the limits and
  operating strategies for 300 to 1,500 consumer repositories.

### Closed-loop governance

- Versioned lifecycle contracts now cover decisions, remediation actions,
  verification, closure, exceptions, metrics and candidates.
- The accepted pilot remains manual and report-only. Guarded automation can
  prepare scoped operational changes without granting autonomous decision or
  waiver authority.

### Repository security and release integrity

- Required Dependency Review, pinned GitHub Actions, restricted workflow
  permissions, CodeQL hardening, critical-path ownership and protected
  operational publication improve the repository security baseline.
- On this private repository, non-dependency changes are scope-checked locally;
  a dependency-manifest change still requires the pinned native review and
  fails closed while GitHub Advanced Security is unavailable.
- Self-Security profile 0.4.0 reports 14 of 16 criteria passing. GRS-002
  (two independent approvals) and GRS-005 (signed changes on `main`) remain open.
- GRS-014 now verifies every current release tag cryptographically. New release
  tags require a direct trusted SSH signature; the fixed historical set remains
  covered by its signed retrospective integrity statement.

## Baseline Compatibility And Migration

| Consumer contract | Supported immutable pin |
|---|---|
| DevSecOps L1 | `l1-baseline-v1.1.3` |
| Architecture L1 | `architecture-baseline-l1-v0.1.0` |

Existing consumers do not need to change these pins. This repository tag is not
a replacement for either baseline tag. No required evidence field, gate
semantic or enforcement default changes in this release.

Operators upgrading the central governance repository should deploy the tagged
revision, keep operational writers on scoped PR paths, configure the required
tokens and reviewers, and verify Pages plus the daily operations workflow. New
consumers must explicitly select report-only operation. Any move to blocking
requires a separate readiness decision and accountable approval.

## Accepted Evidence And Known Limits

The accepted ha-CPsWMS mainline runs report 16 of 16 applicable DevSecOps
controls passing and four of four architecture gates passing. Its measured and
staging evidence consolidates to 11 measured, four partial and one findings
control. All 19 staging checks passed for the isolated VM deployment.

The five accepted image sets contain 749 SBOM components and 2,467 vulnerability
observations, including one critical and 328 high image/package occurrences.
These counts are assessment input, not an accepted risk decision. L1-016 remains
partial pending durable event retention, backup/restore, monitoring and incident
ownership. The DevSecOps replay deviation also remains visible.

All three current consumers remain below the blocking-readiness threshold. The
capacity model shows that the present Git-backed pilot is suitable for its
current scope; operation at 300 to 1,500 consumers requires batched intake,
bounded read models, external immutable evidence storage and, where necessary,
partitioned governance instances.

## Downloads And Integrity

The GitHub Release provides:

- `engineering-governance-whitepaper.pdf`
- `engineering-governance-whitepaper.docx`
- `engineering-governance-presentation.pptx`
- `repository-funktionsweise.pptx`
- `release-manifest.json`
- `SHA256SUMS`

The four publication binaries are intentionally unchanged byte-for-byte from
v0.2.0. The new [source manifest](v0.3.0-public-adoption-assets.json) records
their source paths, sizes and SHA-256 digests for this release. The repository
source and all updated documentation are available from the signed tag archive.

After downloading all six attached files into an empty directory, verify them:

```bash
shasum -a 256 -c SHA256SUMS
```

The checksums bind the downloads to the manifest. The directly signed Git tag
separately binds the repository revision and release statement. Neither check
attests the compliance of a downstream application.

## Validation And Publication Gate

Release preparation uses the pinned validation environment, complete repository
and runtime-governance validation, 623 passing regression tests, strict MkDocs
build, release-manifest verification and direct SSH tag verification. Required
GitHub checks must pass on the preparation PR and the resulting `main` commit
before publication.
