## Changes Since v0.1.0

- Evidence Trust verification, typed vulnerability evidence, digest binding,
  freshness checks, append-only conflict handling and replay triage.
- Multi-consumer indexes, portfolio and readiness projections, a read-only
  governance graph, Intake Health and operation telemetry.
- Collection-attempt history and controlled retry; scoped operational PRs for
  intake and portfolio publication through protected main.
- Daily operations, repository self-security, pinned local validation, CodeQL
  maintenance and practical operating, access and recovery procedures.
- Model-neutral agent roles, deterministic routing and explicit agent provenance.
- Consistent September documentation, a detailed function catalog and refreshed
  executive whitepaper and two editable presentations.

These changes extend the central repository and adoption guidance. They do not
constitute a new released control baseline, an enterprise compliance approval,
or production activation of the signed-attestation pilot.

## Baseline Compatibility And Migration

| Consumer contract | Supported immutable pin |
|---|---|
| DevSecOps L1 | `l1-baseline-v1.1.3` |
| Architecture L1 | `architecture-baseline-l1-v0.1.0` |

Existing consumer pins remain valid and require no migration for this repository
release. Do not replace a baseline workflow pin with the repository release tag.
No existing baseline package or historical tag is rewritten.

For a new pilot, use the `adoption-package/` from this repository release and
record both its revision and the separate baseline pins. Explicitly select
`governance_mode: report-only` for all DevSecOps triggers and
`fail_on_findings: false` for architecture. The released DevSecOps wrapper
defaults to `block-on-error` when the mode is omitted. Review any template
changes before adopting them in an existing consumer.

Operators upgrading the central repository from v0.1.0 must account for the
reviewed operational-write path: an intake run opens a scoped PR, and official
indexes and Pages update after checks, review and merge. Configure the required
cross-repository access and assign reviewers, evidence owners and daily-report
responsibility using the [operations handbook](../operations/guides/governance-repository-operations-handbook.md).
The complete central operating behavior has changed since v0.1.0 even though
the released consumer baselines retain their versions.

## Downloads And Integrity

The GitHub Release provides these existing, validated publication files:

- `engineering-governance-whitepaper.pdf` — eight-page executive whitepaper.
- `engineering-governance-whitepaper.docx` — editable whitepaper.
- `engineering-governance-presentation.pptx` — 12 executive slides.
- `repository-funktionsweise.pptx` — 16 slides explaining the repository.
- `release-manifest.json` — filenames, source paths, sizes and SHA-256 values.
- `SHA256SUMS` — checksums for the four publications and manifest.

The source manifest is [v0.2.0-public-adoption-assets.json](v0.2.0-public-adoption-assets.json).
The source tree is available through GitHub's tag archives. After downloading
all six attached files into an empty directory, verify them there:

```bash
shasum -a 256 -c SHA256SUMS
```

Checksums bind downloaded bytes to this release manifest; the signed Git tag
separately binds the repository revision. Tag verification needs the configured
trusted signer. Neither check attests the quality of downstream application
evidence.

## Validation And Publication Gate

The included documentation/publications were verified with the pinned bootstrap
and `./scripts/validate_all.sh` (234 tests), local green/red demo, strict MkDocs
build, 975 content comparisons and visual inspection of all 28 slides and eight
whitepaper pages. Office exports retain the reviewed bytes and editorial source.

The release-preparation changes require the same repository and strict docs
validation plus asset-manifest/hash checks. Before publication, confirm the
final PR revision has successful required checks, merge with the applicable
review authorization, verify mainline CI and Pages, and create/verify the signed
tag on that merged commit. The GitHub Release records the published tag and
assets. This release introduces no new consumer execution.
