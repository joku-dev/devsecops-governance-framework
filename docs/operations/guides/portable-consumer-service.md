# Portable collector service v1 candidate

This implements persistent collection and proposal coordination for M2 of the platform-portability Goal. The [shared verifier](../evidence/portable-evidence-intake.md) and [operations boundaries](../adapters/portable-operations.md) remain the common execution path. This candidate has no live consumers, configured central endpoint or publisher ownership. It does not update accepted domain indexes or released baselines.

## Configuration and identity

Reviewed source files `config/portable-consumer-profiles.json` and `config/portable-operations.json` are empty by default. Each of at most 2,000 profiles pins its native SCM identity, independent CI identity, baseline/runtime/configuration digests, evidence transport, separate reader credential references and an explicit 1-hour to 7-day discovery lookback. Private operator configuration cannot substitute an arbitrary registry or environment token. The profile JSON schema is `schemas/portable-consumer-registry-v1.schema.json`; the loader additionally checks issuer origins, uniqueness and supported acquisition fields.

The SQLite schema remains v2. `native_tasks` and `portable_http_cache` are additive tables in the same database; existing receipts, legacy jobs/batches, mappings, watermarks and backups are retained. A physical task key binds repository provider/instance/native ID, CI provider/instance, run, physical job, attempt, domain and scope. Producer receipts and bundle bytes keep their original v1/v2 identities. GitHub's logical `GITHUB_JOB` is not rewritten as a REST job ID. The capture records the physical native job; a second physical job mapping to an already consumed producer key is held. The first GitHub profile supports exactly one configured native job name, not arbitrary matrices. GitLab retries have distinct native job IDs and attempt 1. Bamboo job/attempt/Specs/SCM closure remains unresolved and its results remain integrity-only.

`scripts/portable_consumer_intake.py poll|work|status --config PRIVATE.json --root PRIVATE_ROOT --projection PUBLIC_DIRECTORY` is the service entry point. The private config follows `schemas/portable-consumer-service-v1.schema.json`; the example is `infra/ansible/portable-consumer-intake.example.json`. Generate a unique 32-character lowercase hexadecimal node ID for each host. `credentials_directory: systemd` resolves the real service credential mount. Local development can select an absolute private directory instead. Secret files must pass the existing ordinary-file/systemd ACL validator. This initial service uses bearer token files; legacy GitHub App key exchange remains supported by the unchanged legacy engine. Live short-lived-token provisioning/rotation is an operator/provider acceptance item.

## Bounded execution and recovery

Each poll visits at most 25 profiles fairly using a persistent cursor and processes one bounded discovery page per profile. GitHub enumerates workflow runs created within the fixed overlap window; GitLab enumerates pipelines updated within it; Bamboo enumerates completed plan results. Failed runs are included. Discovery revisits overlap windows and deduplicates by native identity, without a latest-success shortcut. Very old GitHub reruns outside the configured creation lookback need explicit historical collection; this is not an unlimited backfill service. Oversized/ambiguous provider pages are rejected rather than silently truncated.

Each worker processes at most 25 tasks under the existing worker lock. An interrupted `working` task returns to `queued`. Ordinary transient failures receive at most three retries; API/budget/storage deferrals do not consume that retry allowance. Per-cycle API requests share the configured budget within an API-origin/credential-subject realm. Poll and work also share a persistent ceiling of 3,000 requests per UTC hour per realm, survive restarts, and honor native rate-limit backoff. These conservative ceilings do not establish provider entitlements or production throughput. A bounded 512-entry conditional-read cache, maximum 256 KiB per entry, is scoped by API origin and credential reference. Only optimization cache entries are evicted; immutable captures and history are retained.

Acquisition first reads untrusted bundle context, then independently reacquires the native run/job/artifact/configuration and SCM facts before invoking the common file/OPA verifier. Original result bytes and Trust are not rewritten. Raw artifacts, audits, failures and receipts are durably written before the processing slot is consumed. One raw-size scan runs per worker cycle; full in-flight file budgets and free-space reserve are checked before each acquisition. The default pilot storage budget and 25 GB VM disk are not a retention sizing promise for 2,000 repositories.

## Shadow, ownership and publication

Private mode starts as `paused`, then can collect in `shadow`. In shadow, central synchronization uses a private read-only Git checkout, compares the installed executable/configuration/IaC dependency closure, reads committed candidate data and executes no fetched scripts or tests. Source drift fails with `application_update_required`. The active Workbench checkout is not reset or repurposed.

Publisher capability requires all of the following: a reviewed central SCM/API/Git profile; credential-free same-origin Git URL; separate API/Git reader and publisher credentials; a source route binding the exact consumer profile digest/domain/scope to one node; at least 24 hours since successful shadow discovery; and an independently collected, newly produced mainline candidate that exactly matches committed central candidate data after that full window. An old result, elapsed timer, `publish` mode, free `approved` flag or local file does not create that comparison. Existing legacy consumer routing must relinquish the same GitHub consumer, and old local/open remote batches or in-flight legacy intake block new work. The empty default routes leave collection ownership with CI.

Candidate documents are allowlisted summaries under `status/portable/v2/candidates/<repository-key>/<native-task-key>.json`. They retain native identifiers and run links but exclude raw provider responses, scanner findings, private paths and credential subjects. A batch freezes the base commit, timestamp, node, at most 25 tasks and exact candidate bytes. Publication modifies only those immutable paths on `automation/portable-consumer/<batch-id>`, never main, historical snapshots or accepted indexes. A lost mutation reply is resolved by reading all native PR/MR states; closed/merged requests are not recreated or reopened. Merge waits for exact bytes on current central HEAD, then marks tasks `reviewed_candidate`, never official compliance. Declined requests remain terminal.

Native CI intake can prepare the identical allowlisted candidate with the existing common CLI: add `--candidate-directory FRESH_PROPOSAL_ROOT` to `intake_portable_evidence.py collect`. It requires complete fresh native provenance and a physical job ID; local imports and Bamboo's unresolved job profile cannot export a review candidate. The command writes candidate data only. Its separately reviewed CI-owned PR provides the committed comparison source during shadow operation; no new scheduled writer or bypass is installed by this change.

## VM installation and schema migration

The existing `scripts/deploy_vm.sh` controller accepts optional private `consumer_engine: portable-v1` and `repository_url: https://internal-mirror.example/axiom.git`. The default `preserve` keeps the installed engine, and a new installation defaults to legacy. The mirror selects installation source only; the central data/push target remains a separate reviewed SCM profile. URLs containing credentials, queries or fragments are rejected.

The portable engine reuses the same poll/work service names, isolated account and private/public directories. Its two timers run one minute after the preceding operation ends. The legacy poll schedule remains unchanged. Provision `/etc/axiom/portable-consumer-intake.json` and root-owned `0600` credential files under `/etc/axiom/portable-credentials/` separately. The poll unit receives only `reader-*`; the worker can receive `publisher-*` after explicit mode/routing selection. No new credentials are copied into source or state backups.

Before any real change, inspect installed revision, mode, current SQLite schema and old native publication identities. Stop poll/work schedules and services, then use the common intake CLI to create a **fresh separate** migration candidate:

```bash
EXACT_VENV/bin/python scripts/intake_portable_evidence.py migrate-legacy \
  --root ORIGINAL_ROOT --destination FRESH_CANDIDATE --legacy-mapping PRIVATE_MAPPING.json
EXACT_VENV/bin/python scripts/intake_portable_evidence.py backup \
  --root FRESH_CANDIDATE --destination FRESH_BACKUP
```

Keep the original root and verified two-location backup. Inspect mappings, old batch IDs/PRs, retained raw files, migration marker and candidate schema before separately authorized activation. The collector does not silently turn a v1 database into v2 or discard old publication work. Use a paused config for the first explicit activation. An interrupted migration cannot start as complete. Moving a backup to a different node/host holds work for reconciliation even if its node ID was copied; paused inspection remains possible.

Installation inspects schema read-only before stopping services. Legacy accepts only absent/v0/v1 state; portable accepts absent/v2 with a compatible target CLI. A schema mismatch or unsupported downgrade stops the update. Existing v2 backups run through the installed exact Python environment and portable backup implementation, retaining migration metadata and original legacy DB. Controller-side manifest verification remains format-neutral. Rollback to legacy requires the explicit `restore-legacy` fresh-root path and reconciliation of later evidence/publications; merely checking out an old commit cannot downgrade the database. Importing Workbench drafts also backs up consumer state with the correct schema-aware implementation.

## API syntax references

The shadow comparison is bound to the verifier source digest. A changed verifier starts a new shadow observation window after successful discovery and invalidates its previous comparison. Existing receipts and decisions remain immutable; old verifier receipts are held for new publication rather than silently renewed or upgraded. Remote automation scans ignore unrelated branches before normalizing repository bindings, so a historical deleted fork does not prevent safe scope reconciliation.

Discovery syntax was checked against the official [GitHub workflow-run API](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow), [GitHub attempt job API](https://docs.github.com/en/rest/actions/workflow-jobs), [GitLab pipeline API](https://docs.gitlab.com/api/pipelines/), [GitLab retried-job API](https://docs.gitlab.com/api/jobs/) and [Bamboo REST 8.2.3 reference](https://docs.atlassian.com/atlassian-bamboo/REST/8.2.3/). GitHub workflow discovery uses the filename, while capture checks the full configured path; windows exceeding the native 1,000-result filtered search ceiling are rejected. Bamboo discovery requests all states and reads completed result `key`, distinct from the queue resource's `buildResultKey`. Missing native Bamboo revision remains unknown; no commit/provenance proof is inferred. These are documented API contracts, not confirmed installed target editions/versions.

## Workbench and acceptance boundary

The public `consumers.json` projection is group-readable `0640`; SQLite, raw files, configuration and credentials stay private. The existing Workbench endpoint reads only that projection. Its portable view labels the five-control pipeline scope, original Trust, native job IDs, provider-specific safe run/PR/MR links, held work and reviewed candidates. It makes no accepted-baseline or compliance assertion.

Deterministic fixtures cover native acquisition, real OPA parity, queue persistence, throttling, raw tampering, ownership/shadow guards, immutable batches, terminal/lost-reply reconciliation and node recovery. The disposable Ubuntu harness exercises the production CLI under real systemd credential mounts and distinct UIDs, including reader/publisher separation and public projection permissions. These tests are not live GitLab/Bamboo/Bitbucket compatibility acceptance. Provider versions, runner/producer pins and live issuance/role authority remain open. [Prepared offline distribution](prepared-runtime-package.md) and the [versioned capacity measurements](portable-capacity-profile.md) have separate engineering evidence. [Provider assurance candidates](provider-assurance-candidates.md) document the native default-branch shadow proof, retained legacy queue notice and additive read model; no prior shadow acceptance is renewed.
